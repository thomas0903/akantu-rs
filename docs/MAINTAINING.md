# Maintaining akantu-rs

Step-by-step procedures for the maintainer and for contributors who take on a
larger change. The rules behind them are in `CONTRIBUTING.md`; how the tests
are organised is in `docs/TESTING.md`; how the C++ oracle is built and run is
in `docs/ORACLE_BUILD.md`.

The port's results are compared with golden data generated by the C++ library
at one commit (`docs/REFERENCE.md`), most of them bitwise, so a change that
moves one bit of a bitwise result fails a test.

CI runs only the fast checks on a pull request (`fast`, `selftest`, `msrv`,
`rustdoc`, `manual`). The feature-gated checks, the MPI, MUMPS and PETSc tiers,
the Python package, memcheck and coverage run weekly (`ci/github/README.md`).
When a pull request touches what a weekly workflow checks, dispatch that
workflow on the pull request's branch before merging (Actions, the workflow,
"Run workflow", the branch). A pull request from a fork has no branch in the
repository: push its head to a branch of the repository first, or run the
tiers locally with `ci/run-all.sh`.

| The change touches | Run before merging |
|---|---|
| cargo features, feature-gated code, release-only tests, convergence studies | `features.yml` (or `ci/run-all.sh --backend docker --preset features` and `--tiers exportall`) |
| parallel code, the solvers, MUMPS or PETSc, the optimised-build tests | `medium.yml` (or `--preset medium`) |
| the Python package or the bindings | `python.yml` (or `--preset python`) |
| `unsafe` code or a foreign function interface | `features.yml`, `memcheck.yml`, and `expensive.yml` for Miri |
| packaging, versions, `Cargo.lock` | `packaging.yml` |

## Adding a material (constitutive law)

The worked example and the trait reference are in the manual chapter
`docs/manual/src/new-constitutive-laws.md`. A built-in solid material:

1. Find the upstream class (`src/model/solid_mechanics/materials/` or
   `extra_packages/`) and its parity row in `docs/FEATURE_PARITY.md` (area
   MAT, or XMAT for the extra materials). Add a row if there is none.
2. Write the law in `crates/akantu-solid/src/materials/<law>.rs` (extra
   materials: `crates/akantu-extra-materials/src/`): a struct generic over the
   dimension, implementing `Material`, with its parameters in a static table
   under the upstream names (the macros `real_param!` and its relatives in
   `crates/akantu-solid/src/materials.rs`). Keep upstream's operation order in
   `compute_stress`, `compute_tangent_moduli` and the energies.
3. Add a `pub fn register(factory: &mut MaterialFactory) -> Result<()>` that registers the
   law under its upstream keyword, declare the module in
   `crates/akantu-solid/src/materials.rs`, and call `register` from
   `register_builtin_materials` in `crates/akantu-solid/src/material.rs`.
4. Golden data: add the cases to `oracle/probes/python/material_cases.py` and
   generate them on the oracle (`oracle/scripts/generate-fixtures.sh
   material:<case_id>`, "Adding or regenerating fixtures" below). They land in
   `fixtures/material/<law>/`. Add a rule to the area's `tolerances.json` only
   if a comparison cannot be bitwise ("Changing a tolerance").
5. Tests: port upstream's test of the law (named after it), a differential
   test on the new cases, and independent checks (tangent against a finite
   difference of the stress, a patch test, energy consistency).
6. Documentation: a page under `docs/manual/src/laws/` and the law's entry in
   the catalogue. The manual's generated tables, including the list of
   registered laws, are refreshed with
   `AKANTU_BLESS_MANUAL=1 cargo test -p akantu --test manual`; review the diff.
7. Update the parity row (Rust location, tests, fixture, tolerance) and run
   `python3 scripts/parity/stats.py --update`. Add a `CHANGELOG.md` entry.
8. Run `cargo test -p akantu-solid --locked`, `cargo test -p akantu --test
   manual`, then the pull-request command of `CONTRIBUTING.md`.

The diffusion, phase-field and contact models have their own law factories
(`registered_law_infos` in `crates/akantu/tests/manual.rs` lists them); a law
for one of them follows the same steps in its crate.

## Adding an element type

1. Add the variant to `ElementType` in `crates/akantu-core/src/element_type.rs`
   with its tables (kind, geometric type, number of nodes, facets, the
   upstream name used in input files and meshes).
2. In `crates/akantu-fe`: the element class in `src/element_class.rs` (and the
   arm of the `with_element_class!` dispatch macro), the shape functions and
   their derivatives in `src/lagrange.rs`, the quadrature rule in
   `src/quadrature.rs`, and the geometric helpers in `src/geometry.rs`. Follow
   upstream's node order and quadrature-point order.
3. Mesh input and output: the Gmsh and Diana type numbers in
   `crates/akantu-io/src/mesh_io/tables.rs` and the VTK cell type and node order
   in `crates/akantu-io/src/dumper/vtk.rs`.
4. Golden data: run the element and FE probes on the oracle in one invocation
   (`oracle/scripts/generate-fixtures.sh element fe_engine fe_extra`; the
   generator checks for stale cases only when the three run together). The
   cases land in `fixtures/fe/`.
5. Tests: partition of unity, the derivatives against finite differences, the
   integration of polynomials up to the rule's order, and the differential
   tests of `crates/akantu-fe/tests/`.
6. Parity rows (areas ELEM and QUAD), `python3 scripts/parity/stats.py
   --update`, `CHANGELOG.md`. The compiler reports each exhaustive `match`
   on `ElementType` that lacks the new variant; search for the matches with a
   wildcard arm as well.

## Adding a dumper field

For the solid mechanics model:

1. Map the field name to a descriptor (source, support, value type) in
   `solid_mechanics_field` in `crates/akantu-io/src/dumper/dumpable.rs`. Use
   upstream's name and component layout (`src/model/solid_mechanics/
   solid_mechanics_model_io.cc`).
2. If the field reads model state that the resolver does not reach yet, add it
   to the model's `FieldResolver` in `crates/akantu-solid/src/model/io.rs`
   (for a nodal field, `nodal_real`). The other models keep their resolver in
   their `model/io.rs` or equivalent.
3. Golden output: the dumper probes in `oracle/probes/dump/` write the C++
   VTU files; the cases are in `fixtures/dump/` with their own `SHA256SUMS`.
4. Test the field against the probe's output with the existing dump tests of
   `crates/akantu-io/tests/` and the model's tests. Update the parity row (area
   DUMP) and the manual's output chapter (`docs/manual/src/output.md`).

## Fixing a bug that changes results

First find out whose bug it is.

- The port differs from the C++ library on a case the C++ library computes
  correctly: the port is wrong. Fix it until the fixture comparison passes
  again; no fixture changes. Add a regression test.
- The port reproduces the C++ library, and the C++ result is wrong: this is an
  upstream defect. Continue below.

For an upstream defect:

1. Collect the evidence: the upstream code, an oracle run that shows the
   behaviour (a probe under `oracle/probes/`), and an independent reference
   (an analytical solution, a conservation law, a patched oracle for undefined
   behaviour, `docs/ORACLE_BUILD.md`, "Patched oracle variants").
2. Classify it under D-003 (`docs/DECISIONS.md`): category A (undefined
   behaviour), B (wrong results) or C (quirk of behaviour, kept by default).
   Moving a defect from C to B changes default results and needs the
   maintainer's agreement.
3. Add or update its entry in `docs/UPSTREAM_DEFECTS.md`: id (`UD-<n>`, the
   next free number), category, upstream location, description, what the port
   does, the switch, the tests.
4. Implement the correct behaviour as the default. For category B, keep
   upstream's behaviour behind a compatibility switch where that is practical
   (the existing switches are listed in the register and in
   `docs/manual/src/differences.md`). The existing differential tests set the
   switch and keep comparing against the unchanged fixtures, so the fixtures
   stay as they are. Add tests of the corrected default against the
   independent reference.
5. Document the change: the manual's differences chapter, the parity row's
   discrepancy cell, and `CHANGELOG.md` under "Changed", stating that default
   results change and how to get upstream's behaviour back.

## Adding or regenerating fixtures

1. Build the oracle at the pinned commit (`docs/ORACLE_BUILD.md`). The
   authoritative platform is x86_64 Linux in the pinned image (D-043). That
   image is not published and its Debian packages are not version-pinned:
   build it with `oracle/scripts/build-image.sh`, which reports package
   drift, and before recording any new case regenerate committed cases and
   check that they are byte-identical (`docs/ORACLE_BUILD.md`, "Checking that
   a regeneration is byte-identical"). Set
   `AKANTU_SRC_HOST` to a clean checkout of the reference commit; every oracle
   script refuses any other state.
2. Write or extend a probe under `oracle/probes/<area>/` (C++, or Python
   through `oracle/probes/python/`). It writes cases with the fixture writer
   (`docs/NUMERICAL_VALIDATION.md` describes the format).
3. Generate into a scratch clone, never into a checkout with work in it:
   `oracle/scripts/generate-fixtures.sh <target>` or
   `oracle/probes/<area>/generate.sh --out <dir>`, restricted to your cases
   with `<AREA>_PROBE_CASES=<id>,…`. Each case runs at least twice and is
   promoted only if the runs are identical.
4. For a regeneration of committed cases, check that the bytes are unchanged
   (`docs/ORACLE_BUILD.md`, "Checking that a regeneration is byte-identical")
   and compare differences with
   `cargo run -p akantu-validation --bin fixture-diff -- <root_a> <root_b>`.
5. Copy back only the cases you own, with their `SHA256SUMS` lines, and run
   `ci/run-all.sh --tiers fixtures`.
6. A case that copies an upstream file (a mesh, a `.dat` file) needs the
   upstream data manifest regenerated:
   `python3 scripts/gold/upstream_data_manifest.py` (check with `--check`).
7. Meshes from Gmsh depend on the platform; fixtures use the frozen meshes of
   `fixtures/meshes/`, regenerated only with
   `oracle/probes/mesh_io/freeze-meshes.sh`.

## Changing a tolerance

A tolerance changes only when a comparison cannot be bitwise for a reason you
can state (a different but valid summation order in a solver back-end, a
platform's libm, a reordered numbering) and the evidence shows the size of the
difference.

1. Edit the rule in the area's `tolerances.json`: the quantity pattern, the
   kind of rule (ULP, relative, norm-wise, reordering), the bound, the
   justification and the evidence (the measured difference, the case, the
   platform).
2. Regenerate the ledger: `python3 scripts/gold/tolerance_ledger.py`, and check
   it with `--check`. The tests `tolerance_ledger` and `tolerance_files` of
   `akantu-validation` read both.
3. Describe it in the area's section of `docs/NUMERICAL_VALIDATION.md`.
4. A loosened rule needs a second person's review. Never loosen one to make a
   failing test pass without knowing why it fails.

## Following a new upstream commit

The authoritative copy of the pinned commit is `docs/REFERENCE.md`. The hash is
also written into code and scripts, and into every fixture's provenance. Find
the copies with:

```sh
git grep -l 35a851780d0b9471d258ed53a003ae98aaa95ea0 -- ':!fixtures'
git grep -l 35a85178 -- ':!fixtures'
```

The copies that act on something are the oracle scripts' pin
(`AKANTU_REF_SHA` in `oracle/scripts/common.sh`, `REF_SHA` in
`oracle/scripts/generate-fixtures.sh` and
`scripts/gold/upstream_data_manifest.py`), `REFERENCE_SHA` in
`crates/akantu-validation/src/regression.rs`, `UPSTREAM_VERSION` in
`crates/akantu/src/lib.rs` (the `git describe` name) and the oracle image
(`oracle/docker/`). The others are provenance and documentation.

1. List what changed:
   `git -C <akantu-src> log --oneline <old>..<new>` and
   `git -C <akantu-src> diff --stat <old> <new> -- src extra_packages python test examples`.
2. Map each changed upstream file to parity rows: search the matrix's column
   of original files and symbols, and the inventories (`docs/inventory/`), for
   the file's path. Note the rows and the fixtures their tests read.
3. Read the changed rows' upstream changes against the defects register: a
   defect fixed upstream changes what the port must reproduce.
4. Build a second oracle at the new commit (a new image tag and build volume,
   `docs/ORACLE_BUILD.md`) and regenerate the affected fixtures into a scratch
   tree. Compare them with the committed ones using `fixture-diff`: unchanged
   physics must give byte-identical data.
5. Port the changes row by row, one pull request per subject, each with its
   regenerated fixtures and tests.
6. When everything follows the new commit, move the pin: update the copies
   listed above, `docs/REFERENCE.md`, `docs/ORACLE_BUILD.md`, the manual's
   upstream-changes page (`docs/manual/src/upstream-changes.md`) and
   `CHANGELOG.md`. Regenerate the upstream data manifest. Then run every tier
   ("Cutting a release", step 2).

## Updating a dependency without changing results

Cargo dependency updates are not automated, because a new version of a numerical
crate (`faer` above all, or `serde_json`, whose float parsing the fixtures
rely on) can change floating-point results.

1. Update one dependency at a time:
   `cargo update -p <crate> --precise <version>`. For a version outside the
   requirement, change `[workspace.dependencies]` in `Cargo.toml`.
2. Check its licence and the GPL separation: `ci/run-all.sh --tiers licence`;
   record a new licence in `ci/licence-policy.toml` only after review, and update
   `docs/DEPENDENCIES.md`.
3. Run the fast tier and the weekly workflows that build the dependency
   (`features.yml` for optional native bindings, `medium.yml` for anything in
   the solvers, `python.yml` for PyO3 and NumPy). Every bitwise comparison must
   still pass. If one moves, the update changes results: pin the old version
   and open an issue.
4. Check the MSRV (`msrv` job). A dependency that needs a newer Rust raises
   `rust-version`, which is a user-visible change for `CHANGELOG.md`.

Dependabot (`.github/dependabot.yml`) proposes updates of the GitHub Actions
only. When you accept one, copy the changed workflow from `.github/workflows/`
to `ci/github/` (or make the change there and copy it back): `ci/selftest.sh`
requires the two to be identical.

The first Dependabot pull request (14 November 2026, four action bumps)
showed what this means in practice: Dependabot changes only
`.github/workflows/`, so the pull request's `selftest` job fails until the
same bump is copied into `ci/github/`. Mirror it on the pull request's
branch, update the list of pinned versions under "Repository settings" in
`ci/github/README.md`, run `ci/selftest.sh`, and commit:

```sh
gh pr checkout <number>
cp .github/workflows/*.yml ci/github/
```

## Editing the manual

The manual (`docs/manual`) is built with mdBook 0.4.40 and the preprocessor
mdbook-katex 0.9.4 (`cargo install mdbook --version 0.4.40 --locked`,
`cargo install mdbook-katex --version 0.9.4 --locked`, then `mdbook build
docs/manual`; D-122).

1. Formulas are LaTeX: `$...$` inline, `$$...$$` on lines of their own for a
   displayed formula, with no blank line inside. A formula that KaTeX cannot
   parse does not stop `mdbook build`: it prints "Rendering failed" and
   leaves the source in the page. `ci/github/manual-build.sh <dir of the two
   binaries>` is what the CI runs, and it fails in that case. An expression
   whose point is the order of its floating-point operations stays a code
   block. A literal dollar sign in the text is written `\$`.
2. A figure is an image followed, on the next line of the same paragraph,
   by its caption in emphasis. Drawings made for the manual are SVG files in
   `docs/manual/src/figures/`; figures copied from Akantu are in
   `figures/upstream/`, whose `NOTICE` names their origin; a copied file
   that no page shows is removed. The caption of a result image says which
   library computed it.
3. The images of `figures/examples/` are results of the port's examples,
   rendered by `scripts/manual/render_figures.py` (its header gives the
   commands: build and run the examples, then render off-screen in a
   container). Render them again when an example's output changes. The
   script is a maintenance tool; neither the build nor the CI runs it.
4. Run `cargo test -p akantu --test manual` (links, anchors, generated
   tables, keyword tables) and, if a Rust block changed, `cargo test -p
   akantu --doc`. The element appendix is generated, formulas included:
   change the generator in `crates/akantu/tests/manual.rs` and regenerate
   with `AKANTU_BLESS_MANUAL=1 cargo test -p akantu --test manual`.

## Cutting a release

1. Choose the version (semantic versioning; before 1.0 a change of default
   results or of a public API raises the minor version). Set it in
   `[workspace.package]` of `Cargo.toml`; every crate and the Python package
   take it from there.
2. On the release commit, dispatch every workflow: `fast` and `docs` run on
   the push, then dispatch `features`, `medium`, `python`, `packaging`,
   `memcheck`, `coverage`, `distro` and `expensive`. All must pass; `distro` is
   diagnostic and its failures are read.
3. In `CHANGELOG.md`, give the section of the version its date (the first
   release's heading reads "[0.1.0] - Unreleased"; later changes collect under
   "Unreleased" and move to a new section `[<version>] - <date>`), update
   `version` in `CITATION.cff` and add a `date-released` field there.
4. Tag the commit with an annotated tag `v<version>` and push the tag. The tag
   runs `fast.yml` and `packaging.yml`; the `version` tier checks that the tag
   equals the workspace version.
5. Create the release on the hosting platform with the changelog section as
   notes. The wheels of the tag's `packaging` run are artifacts for 14 days;
   attach them if they are part of the release. Nothing is published to
   crates.io or PyPI (every crate has `publish = false`).

## Routine

- Read the weekly results every week. A failure on `main` is fixed or
  recorded in `ci/tools/known-failures.txt` with its reason before more
  changes merge.
- Keep the generated blocks current (`python3 scripts/parity/stats.py
  --update`, `python3 scripts/gold/tolerance_ledger.py`,
  `AKANTU_BLESS_MANUAL=1 cargo test -p akantu --test manual`); the fast tier
  fails when they are stale.
- `python3 scripts/unsafe_inventory.py --check --strict-safety` after any
  change near `unsafe` code; `--update-lines` when code only moved.
