# Cohesive scalability test — correctness reference (C++ oracle, strict)

Physical outputs of the Akantu JOSS cohesive scalability driver
(`benchmarks/cohesive-perf/src/cohesive_extrinsic.cc`) on a small cube, for
the future Rust driver. Generated by
`benchmarks/cohesive-perf/scripts/gen-fixtures.sh --steps 1500 --reps 3`
with the `strict` oracle build (`-ffp-contract=off -DEIGEN_DONT_VECTORIZE`,
`docs/ORACLE_BUILD.md`); full provenance in `provenance.json`.

**Status: preparatory data, not golden fixtures.**
These are plain CSV/JSON files without `manifest.json` or `tolerances.json`:
a bounded exception to the fixture format of `docs/NUMERICAL_VALIDATION.md`,
limited to this directory and to the Rust cohesive driver's bring-up.
Every output file carries a machine-readable label in `qualification.json`
(`qualified` = bitwise identical over the 3 fixed-seed runs, D-035(b);
`diagnostic` = not repeatable, unqualified data). **Gate before any golden
or parity use:** (1) only `qualified` files; (2) a manifest and tolerance
rules per `docs/NUMERICAL_VALIDATION.md`, independently reviewed; (3) the
scope stays this mesh, these 1500 steps, these rank counts and modes.
`python3 -I benchmarks/cohesive-perf/scripts/make_fixtures.py --check`
validates the directory offline (histories, counts, labels).

## Inputs

* `meshes/cube-h0.12.msh` — frozen Gmsh 4.13.1 mesh (D-009) of
  `benchmarks/cohesive-perf/inputs/cube.geo` with `h = 0.12`: 4 824 nodes,
  23 156 tetrahedra, 2 798 boundary triangles, 34 segments.
* `<case>/input.dat` — the upstream `material-{cohesive,elastic}.dat` with
  `mesh = ../meshes/cube-h0.12.msh` (relative to the case directory),
  `max_steps = 1500`, `output_energy = true` and `energy_precision = 17`
  (17 significant digits in `energies.csv`); the 2-rank cases also set
  `export_partition = true`, `coh_np2_global` sets `blocked_node = global`.
  Material, boundary conditions and the shear increment schedule (every 100
  steps) are the upstream ones. Runs: `AKA_SEED=1`, `SCOTCH_PTHREAD_NUMBER=1`
  (reproducible Scotch partitions, see `benchmarks/cohesive-perf/README.md`).

## Cases

| Case | Problem | Ranks |
|---|---|---|
| `coh_np1` | cohesive insertion on (`material-cohesive.dat`) | 1 |
| `ela_np1` | no insertion (`material-elastic.dat`): finite-deformation elastic, explicit | 1 |
| `coh_np2` | cohesive insertion on, upstream rule (local node 3 of each rank blocked in y), partition in `partition.csv` | 2 |
| `coh_np2_global` | cohesive insertion on, `blocked_node = global` (the 1-rank problem), partition in `partition.csv` | 2 |

Files per case: `energies.csv` (step 0 = after the static solve, then every
step: dissipated `ed`, potential `ep`, kinetic `ek`, accumulated external
work `ew`, `et = ed + ep + ek − ew`), `insertions.csv` (every step with
insertions and the value `checkCohesiveStress()` returned, with its running
total; at 1 rank this is the global number of new cohesive elements and the
total equals `nb_cohesive_elements`; **at 2 ranks the value also counts the
ghost copies** of elements inserted on partition boundaries (UD-347), so the
total (418) exceeds the true global count (404, `summary.json`); the
insertion *steps* are exact at any rank count), `summary.json` (Δt, final energies, L2
norm / max / sum of the displacement over owned nodes, node/element/cohesive
counts, modes), `summary_rank<r>.json` (local counts, blocked node(s) with
local/global id and coordinates, number of `fillNodesToElements` event calls),
`partition.csv` (2-rank cases: Scotch partition of every element of the
global mesh, in Akantu's element order per type).

The benchmark's first 200 steps (requested as the minimal P = 1
differential check) are steps 0–200 of `coh_np1/energies.csv`; no element is
inserted before step 710 on this mesh (`first_insertion_step`), so steps
710–1500 add the insertion onset (404 cohesive elements, 294 insertion
steps, E_diss = 3.1237 J at step 1500; Δt = 1.627144031722343e-07 from
`getStableTimeStep()` × 0.05 after the static solve).

**Rank count changes the problem**: the driver blocks `y` of the *local* node
3 of every rank (`blocked_dofs(3, _y) = true`), so `coh_np2` is not the
1-rank problem split in two. A Rust driver must apply the same rule on the
same partition (`partition.csv`) to be compared with `coh_np2`.

## Determinism, qualification and sensitivity (measured)

`determinism.json` (per-repetition SHA-256 of every file, energy
differences of the non-identical repetitions), `qualification.json` (labels
derived from those digests by `make_fixtures.py --qualify-committed`) and
`sensitivity.json` (diagnostic comparisons). All numbers are relative
differences |a − b| / max(|a|, |b|) per energy column, maximum over the
steps up to the one named.

| Case | Qualified (bitwise over 3 runs) | Diagnostic (not repeatable) |
|---|---|---|
| `coh_np1`, `ela_np1` | every file | — |
| `coh_np2` | `partition.csv`, `insertions.csv`, `summary_rank0/1.json` | `energies.csv`, `summary.json` (energies, displacement norms) |
| `coh_np2_global` | `partition.csv`, `insertions.csv`, `summary_rank0/1.json` | `energies.csv`, `summary.json` |

The 2-rank energies differ in one of the three runs from step 0 (the 2-rank
MUMPS static solve is not bitwise reproducible, UD-348; the 1-rank solve
is): measured repeat variation at step 800 ≤ 1.7e-13 (`ek`), 3.1e-12
(`ew`), ≤ 6e-16 (`ep`, `et`), `ed` = 0; at step 1500 `coh_np2`: `ed`
2.5e-6, `ek` 4.1e-9, `ep` 2.7e-10, `et` 3.6e-10, `ew` 6.2e-10;
`coh_np2_global`: `ed` 4.3e-9, `ek` 2.1e-12, `ep` 1.2e-13, `et` 1.4e-13,
`ew` 1.4e-12. Three samples are not an upper envelope (an independent review measured
`ed` 2.1e-8 for one more `coh_np2_global` run): under D-035 these energies
are **diagnostic only**, and no tolerance is proposed for them.

Comparisons, kept apart:

* **Same-partition reproduction** (a re-run of `coh_np2` or
  `coh_np2_global`: same `partition.csv`, same rule): the qualified files
  must be reproduced exactly; the energies only within the measured
  run-to-run variation above (diagnostic).
* **Explicit partition vs upstream `mesh.distribute()`** (`coh_np2`): same
  insertion steps and counts (enforced at generation); energies within the
  2-rank run-to-run variation (diagnostic).
* **JOSS-patch emulation vs upstream** (`coh_np1`): bitwise identical
  energies and insertions (enforced at generation).
* **Cross-rank physics** (`coh_np1` vs `coh_np2_global`, the same problem
  at 1 and 2 ranks; diagnostic, measured on P = 2, this mesh, 1500 steps,
  `blocked_node = global` only): ≤ 5.5e-15 (`ep`, `et`), 3.5e-13 (`ek`) up to
  step 800; divergence from step ≈ 900 (> 1e-9 at steps 905–912), 8.1e-6
  (`et`), 6.1e-6 (`ep`), 5.7e-8 (`ed`) at step 1500; the same final counts
  (404 cohesive elements, 294 insertion steps) in this single comparison, but
  insertion steps differ from step 1043; Δt rel. 3e-16. Not a rule for other
  rank counts, meshes, windows or modes.
* `coh_np1` vs `coh_np2` (upstream rule): different problems, not
  comparable (Δt rel. 2e-10, `ek` 3e-5 from step 1, `ed` 9e-3 at step 1500).

FP sensitivity of the serial cases (strict vs default build, FMA
contraction): `coh_np1`: Δt and insertion sequence identical; steps 0–800:
`ep`, `et` ≤ 1.4e-14, `ek` ≤ 1.4e-13, `ew` ≤ 7.5e-12 (tiny early values),
`ed` = 0; step 1500: `ed` 1.6e-9 (first > 1e-12 at step 842), `ek` 7.9e-13,
`ep` 4.7e-14, `et` 6.6e-14; final displacement norm 3.1e-14. `ela_np1`: ≤
1.4e-13 (`ek`), 1.5e-14 (`ep`, `et`), 7.5e-12 (`ew`) over all 1500 steps.

## Proposed serial tolerances (PROPOSED: they need an independent review, docs/NUMERICAL_VALIDATION.md)

Class `time_integration` (docs/NUMERICAL_VALIDATION.md), recorded as
`PROPOSED`:
bounds set at ≈ 10× the measured FP-perturbation variation above, for
`coh_np1` / `ela_np1` only, this mesh and steps 0–1500. They assume the
Rust port follows the same algorithms (same quadrature, same lumped mass,
same stable-Δt rule with current positions, same insertion criterion and
order); a port that reassociates sums more aggressively than FMA
contraction may need its own baseline. **These are proposals, not reviewed
rules.** **On hold (x86_64 evidence):** the Δt, `ed` (steps
801–1500) and `ek` (steps 801–1500) proposals are exceeded by the x86_64
strict-vs-default perturbation (`ed` 6.9e-8, `ek` 3.4e-11) and by the
x86_64-vs-aarch64 strict difference (Δt 1.8e-14, `ed` 3.4e-8, `ek` 1.7e-11),
see `../perf_cohesive_x86_64/README.md`; they must be re-derived from x86_64
baselines (D-043) and reviewed before any use. The other rows are within
the x86_64 measurements.

| Quantity | Proposed rule | Evidence |
|---|---|---|
| Δt (`summary.json` `time_step`) | rel ≤ 1e-14 | strict = default bitwise; a min over elements of a closed-form expression |
| node/element counts, `nb_cohesive_elements`, insertion steps and counts (`insertions.csv`) | exact | identical under the FMA perturbation through step 1500 |
| `ep`, `et`, steps 0–800 | rel ≤ 2e-13 | ≤ 1.4e-14 |
| `ek`, steps 0–800 | rel ≤ 2e-12 | ≤ 1.4e-13 |
| `ew` (accumulated external work) | rel ≤ 1e-10, or abs ≤ 1e-12 · max over steps of abs(ew) | ≤ 7.5e-12 (pointwise, driven by tiny early values) |
| `ed`, steps 0–800 | exact zero | no insertion before step 710, no opening before 839 |
| `ep`, `ek`, `et`, steps 801–1500 | rel ≤ 1e-11 | ≤ 7.9e-13 |
| `ed`, steps 801–1500 | rel ≤ 2e-8 | ≤ 1.6e-9 (grows from step 842) |
| final displacement L2 norm / max / sum | rel ≤ 1e-12 (sum components: abs ≤ 1e-12 · ‖u‖₁ scale) | 3.1e-14 |
| `ela_np1`, all steps | `ep`, `et` rel ≤ 2e-13, `ek` ≤ 2e-12, `ew` as above | no growth observed |

**No 2-rank rule is proposed** (the earlier "P = 2 or any P" band and the
±1 % count allowance are withdrawn after an independent review): the 2-rank energies
are diagnostic under D-035, the qualified 2-rank files (partition,
insertion steps, per-rank counts) compare exactly, and a cross-rank
tolerance would need a workload-specific policy amendment backed by more
runs and its own review. Insertion counts at different rank counts in the
upstream (local node 3) mode are **not** comparable.

## Regeneration

`benchmarks/cohesive-perf/scripts/gen-fixtures.sh --steps 1500 --reps 3`
(oracle runs on an x86_64 Linux machine) runs
the cases and `make_fixtures.py`, which validates **every attempt** before
writing anything (`attempts.json`: exit status and decision per attempt):
UD-216 / MUMPS messages in stdout or stderr, missing logs, run identity
(config, ranks, steps, seed, Scotch threads, interposer mode, parameters,
frozen-mesh digest, exact input), truncated or non-finite histories,
inconsistent counts and final energies, Chrono row, build record identical
for all runs of a build (PF-08: provenance comes from the runs' own build
records, never from the current build directory). It enforces the serial
repeatability, the partition repeatability and the two equivalences above,
labels every file, writes into a staging directory and replaces the target
only when everything passed. It refuses to replace existing cases without
`--replace` (committed golden files are never replaced without orchestrator
approval); a regeneration on another platform goes to its own directory
(`--out perf_cohesive_x86_64`, done: `../perf_cohesive_x86_64/`). The committed files were generated before
these checks existed (aarch64, 2026-11-10); `make_fixtures.py --check` and
the unit tests (`benchmarks/cohesive-perf/scripts/tests/`) re-validate them.

## Eigen-solver variants `coh_np1_eigen`, `ela_np1_eigen`

The references of the Rust driver's bitwise replay
(`crates/akantu-bench/tests/perf_cohesive_fixture.rs`, exact rule, endorsed
by an independent review for aarch64 and, with D-050, x86_64). They are outside the
"preparatory" status above: D-035(b)-qualified (three byte-identical
repetitions, digests in `eigen_variant.json`) and used under the exact rule
only. They are not listed in `qualification.json` (which labels the MUMPS
cases of `make_fixtures.py`); `make_fixtures_eigen.py --check` validates
them. Same runs as `coh_np1` / `ela_np1` (strict build, frozen h = 0.12
mesh, 1,500 steps, `energy_precision = 17`, `AKA_SEED=1`) except that the
static solve uses Eigen's SparseLU (`sparse_solver_type = eigen` in the
`time_step_solver static` section of `input.dat`) instead of upstream
`_auto` = MUMPS: the port's `eigen` backend translates that solver
operation for operation, so the whole run can be compared bitwise without
MUMPS.

* **Generation:** `benchmarks/cohesive-perf/scripts/gen-fixtures-eigen.sh
  --steps 1500 --reps 3` (runs through the validated `run-one.sh` with
  `PERF_STATIC_SPARSE_SOLVER=eigen`, which adds `sparse_solver_type = eigen`
  to the static solver section and records it in `run.json`) and
  `make_fixtures_eigen.py` (validation, files, `eigen_variant.json`,
  SHA256SUMS lines). Committed data: aarch64
  (OrbStack), strict install, image `sha256:6683233d…`, generated
  2026-11-10T23:44Z; the three repetitions are byte-identical
  (`eigen_variant.json` digests; D-035).
* **Provenance caveat:** `eigen_variant.json` records
  `harness_git_dirty: true` (the work in progress was uncommitted
  at generation). The content is confirmed independently: an independent review
  regenerated both cases on x86_64 with the D-050 Eigen cache pin and got
  `energies.csv` and `insertions.csv` byte-identical, Δt identical
  (`1.6271440317223231e-07`). The generator now refuses a dirty harness tree
  (`--allow-dirty` records the `git status` lines instead).
* **Validation** (the checks two independent reviews asked for): every repetition
  must have exit status 0, the requested step count, an Eigen static solve
  (run metadata and input), no MUMPS message in its logs, a complete energy
  history (rows 0…N consecutive, all values finite), an insertion list
  consistent with `summary.json` (increasing steps, positive counts, running
  total = `nb_cohesive_elements`, rows = `nb_insertion_steps`, first step =
  `first_insertion_step`) and finite summary values.
  `python3 -I benchmarks/cohesive-perf/scripts/make_fixtures_eigen.py --check`
  validates the committed cases offline (both pass: 1,501 consecutive rows,
  404 cohesive elements in 294 insertion steps from step 710, resp. none);
  `scripts/tests/test_make_fixtures_eigen.py` pins the refusals.
* **x86_64 regeneration needs D-050** (`docs/ORACLE_BUILD.md`): Eigen
  sizes the SparseLU blocking from the CPU cache sizes, which an unpinned
  x86_64 build queries with CPUID. Unpinned (EPYC 9455, L1 64 KiB) the
  oracle differs from these files (measured by an independent review: Δt rel 1.8e-14, `ep`
  from step 0, `ed` 5.9e-7 at step 1500, same insertion sequence); with the
  cache sizes pinned to 16384 / 524288 / 524288 it is byte-identical, so
  these aarch64 files are also the x86_64 reference under D-050. On a
  non-aarch64 image `make_fixtures_eigen.py` refuses an install whose driver
  compile command lacks `-DEIGEN_NO_CPUID` and the three cache-size defines
  (fail-closed: the driver instantiates Eigen code itself, so the defines
  must reach its compile command as well as the library's; not yet
  exercised against the pinned x86_64 install); when the
  x86_64 corpus is regenerated, these two cases belong in it, pinned.
* **Eigen vs MUMPS** (oracle against itself, `eigen_variant.json`): Δt rel
  1.2e-14; `coh_np1`: same insertion sequence; up to step 800 `ep`, `et`
  ≤ 4.9e-15, `ek` ≤ 7.0e-13, `ew` ≤ 4.4e-11, `ed` = 0; up to step 1500 `ed`
  ≤ 5.8e-7, `ek` ≤ 2.8e-10, `ep`, `et` ≤ 1.9e-11; `ela_np1`: ≤ 7.0e-13 (`ek`),
  5.0e-15 (`ep`, `et`), 4.4e-11 (`ew`) over all steps. The Rust driver
  reproduces the Eigen variants bitwise, so these are exactly its
  differences from the MUMPS cases.
* **Insertion count of the Rust driver:** `insertions.csv` holds the global
  number of cohesive elements inserted at each step, taken from the mesh
  (not-ghost cohesive elements summed over the ranks). At
  one rank this equals upstream's `checkCohesiveStress()` value (checked at
  every step); at more ranks upstream's value also counts ghost copies
  (UD-347, "Cases" above), the Rust driver's does not.
